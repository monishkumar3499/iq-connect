IQ Connect Architecture

A fresh design for one Claude connector over Fabric, Databricks and Snowflake. People sign in with company SSO, create named connections, each scoped to the warehouse or model they picked and carrying their own prompt, and edit them later in a settings app. Every tool call runs as that person, inside that connection's scope, read-only.

Your questions, answered

One server or one per platform?

One server. One connector URL, one sign-in, one database, one place to enforce rules. Each platform is an adapter inside it that implements the same functions. Separate servers would mean three sign-ins, three token stores and a proxy between them, which is the complexity in today's hub.

How are people and connections identified?

Claude's token identifies the person, not a connection. A person owns any number of connections (for example "Sales warehouse", "Finance model"), and each tool call names which one to use. Settings are read from the database on every call, so edits in the UI apply on the next call with no reconnect.

Several platforms at once?

Yes, naturally. In one chat, Claude can query the Fabric connection, then the Snowflake one, and compare. Each call carries its connection name; there is no "current platform" to switch.

1,000 users at once?

Nothing about a user lives in server memory. Every request carries a token, the connection is loaded from PostgreSQL, and slow driver calls run in bounded thread pools. Run 3+ identical copies behind a load balancer and add more as needed.

Encrypt with something from Claude's token?

Encrypt: yes. Key from the token: no. We issue that token ourselves, and it changes every hour, so data locked with it could not be unlocked after the next refresh. Use envelope encryption with a key held in Key Vault, bound to the user and connection (details below).

Read-only, and no peeking at other workspaces?

Four layers: the platform's own permissions (queries run as the user), a connection scope allow-list checked on every call, a SQL parser that allows only SELECT inside that scope, and no write tools at all. Any one layer failing still leaves the others.

Connect and set up

  1. The person adds the connector in Claude (one URL) and presses Connect.
  2. Claude opens our /authorize. Our page signs them in with company SSO (Entra). We now know the person: org, user id, email.
  3. If they already have connections, they see them and press Continue. Otherwise they press Add connection.
  4. They pick a platform and sign in to it. For Fabric, the same Entra sign-in also grants delegated Fabric/Power BI access. Snowflake uses OAuth or key-pair; Databricks uses Entra or Databricks OAuth, as today.
  5. We browse with their credential, so they see only what they can already access. They pick the scope: a workspace and a warehouse or semantic model, or a catalog and schema.
  6. They name the connection and write an optional custom prompt. We save it, with credentials encrypted.
  7. We redirect to Claude with a code. Claude exchanges it for a token that identifies the person.
  8. Claude lists tools: the same set for every platform. Each call names a connection.
  9. Later, the person opens the settings app (same SSO) to rename, re-scope, edit prompts, add or delete connections. Changes apply to the next tool call.

One tool set for every platform

ToolDoes
list_connectionsNames, platform, SQL dialect, scope and custom prompt of each of your connections
list_objectsBrowse schemas, tables and views, only inside the connection's scope

query_semantic_modelOnly for connections whose platform supports it (Fabric DAX today); listed with that capability

Same names and parameters everywhere, but SQL itself differs between T-SQL, Databricks SQL and Snowflake SQL. That's why list_connections reports each connection's dialect, and errors say which dialect was expected. The custom prompt is returned by list_connections and repeated in that connection's results, so it reaches Claude even though server-wide instructions can't vary per connection.

The adapter contract

class PlatformAdapter(Protocol):
    platform: str                       # "fabric" | "databricks" | "snowflake"
    dialect: str                        # "tsql" | "databricks" | "snowflake"
    capabilities: set[str]              # e.g. {"sql", "semantic_model"}

    # setup wizard
    def browse_scope(cred, path) -> list[ScopeNode]
    # tool calls (scope already checked by the core)
    def list_objects(conn, cred, path) -> list[Obj]
    def describe_table(conn, cred, table) -> Table
    def run_query(conn, cred, sql, limit) -> Rows | QueryId
    def get_result(conn, cred, query_id) -> Rows | Pending
    def tables_in(sql) -> list[QualifiedName]   # for the scope check

The core never knows which platform it's talking to. Adding a fourth platform means writing one adapter.

Read-only and staying inside the scope

LayerHow it's enforcedWhat it stops
1 Platform permissionsQueries run as the user (Fabric OBO, Databricks user token, Snowflake read-only role). Masking, row-level security and grants apply as usual.Anything the user couldn't see themselves
2 Connection scopeEvery table a query touches is resolved to its full name and checked against the connection's allow-list. Browsing tools only list inside the scope.Other workspaces, warehouses, catalogs and schemas the user can see but didn't pick
3 SQL policyA real SQL parser (for example sqlglot, per dialect), not keyword matching: one statement, SELECT/WITH only, no DDL/DML, no procedures, no file or external reads.Writes, multi-statement tricks, escape hatches
4 Tool surfaceNo write tools exist. Read-only driver modes where offered (Fabric ApplicationIntent=ReadOnly).Claude being talked into writing
5 LimitsRow cap, query timeout, per-user and per-org rate limits, warehouse size caps.Runaway cost, bulk extraction
6 Org policyThe company admin sets which platforms and workspaces may be connected at all.Users connecting data the company hasn't approved

Write access, if ever wanted, should be a separate tool set an org admin enables per connection, with platform-side write grants, never by loosening layer 3. Also remember that table contents can contain text that tries to instruct Claude (prompt injection). Read-only access and tight scope keep the possible damage small.

Encrypting stored details

Key derived from Claude's token

doesn't work
  • We issue that token, so it isn't a secret from us.
  • It's replaced every hour, so yesterday's data couldn't be decrypted today.
  • Claude is only present while a tool call is running. The settings app needs the data with no Claude token at all.

Envelope encryption with Key Vault

recommended
  • Each credential gets its own random data key. The data key is wrapped by a master key that never leaves Key Vault.
  • The user id and connection id are bound in as associated data, so a row copied onto another user fails to decrypt.
  • Rotate the master key without re-encrypting everything; revoke it to make every stored secret unreadable.
  • Encrypt the secrets (tokens, keys). Names, scope and prompts are protected by database encryption at rest plus access control.

Storing less beats encrypting more. Prefer OAuth refresh tokens (revocable by the company) over passwords. If Snowflake is set up with External OAuth trusting Entra, all three platforms can use the one Entra sign-in.
